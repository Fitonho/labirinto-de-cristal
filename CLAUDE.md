# Labirinto de Cristal

A small push-and-flip puzzle game in TypeScript. You are a piece of one colour on a board of black and white tiles: tiles of the other colour are floor, tiles of your colour block you and can be pushed, and walking through a portal (a glowing seam on an edge) flips your colour. Reach the crystal while you are the colour it shows. The game is one Expo (React Native) app that runs on Android, iOS and the web; Netlify serves its web export.

## Commands

- `npm install`, then `npm run build`: type-checks and exports the web version into `dist/` (`expo export`, via `scripts/build.mjs`). Netlify runs this.
- `npm start`: Expo dev server; scan the QR code with Expo Go on a phone. `npm run web` opens it in a browser.
- `npm run phone`: the production-like server for phone tests (`--tunnel ngrok --no-dev --minify --clear`); `npm run phone:dev` is the same in dev mode. Dev mode is 5 to 10 times slower, so judge speed with `npm run phone`.
- `npm test`: Vitest, about 10 s; the comparison test is the slow part.
- `npm run typecheck`: `tsc` only.
- `npm run solve -- <level id>`: shortest solution using the real engine. Only use it on small levels (chapters 1 to 4 and the challenges, new 4x4 to 7x7 boards). The 9x9 drafts (the labyrinths) are open-ended, and searching them runs for a long time; the owner asked not to run solvers over them.
- `npm run generate -- --size 6x6 --needs push,portal --par 15-30`: finds new levels (`src/tools/levelGenerator.ts`): random boards climbed toward a longer solution, kept only if the level can't be won without each named mechanic (`push`, `portal`, `carry`, `star-push`), every portal is needed and, with `--stars 2`, each star alone needs a push. Each board is tidied (calmer colours, same solution length) and written to the Lab (`src/levels/lab.json`, replaced unless `--append`) with its solution and a `?board=...` link. Run it with no options for the rest (`--stars`, `--portals`, `--count`, `--time`, `--seed`, `--tag` for the ids). A 5x5 level takes about 40 s.
- Add `?debug` to the page URL to log every Redux action and its engine events to the console. Logging is on in dev (`__DEV__`) and in every web export except Netlify production (`EXPO_PUBLIC_DEBUG_LOGS`, set in `scripts/build.mjs`).
- Expo packages must match SDK 58: take versions from `node_modules/expo/bundledNativeModules.json` (`npx expo install` needs Expo's servers, which the cloud environment can't reach).

## Layout

- `src/core/`: the rules engine. Pure TypeScript with no DOM, no Redux, no timers, no globals and no player-facing text. `move(state, direction)` returns `{ state, events }` and never mutates its input. Everything in `GameState` is plain JSON.
- `src/levels/`: levels as JSON, one file per chapter (`first-steps.json`, `portals.json`, `crystals.json`, `moving-portals.json`, `challenges.json`), listed in menu order by `index.ts`. The Lab (`lab.json`, `lab.ts`) holds the generator's boards with their solutions; it is a chapter everywhere, the live site included, while `LAB_SHOWN` in `index.ts` is true, counts toward no totals, has no fingerprints, and its levels get a Solve button that plays the solution. A `?board=...&start=...&portals=...&solution=...` address opens any board straight away as a Lab level. The labyrinths are the kept boards of `drafts.json`, which stays whole for `compare.test.ts`. Every level in a chapter file has its shortest solution in `tests/engine.test.ts`, and its par is that length (about 10% more in the challenges). On a new board, every portal must be needed and, with two stars, each star alone must need a push. Grid rows use `b` / `w`, uppercase for a crystal; portals are `[row, column, side]`.
- `app/`: Expo Router screens. `_layout.tsx` creates the store; `index.tsx` is the game screen, with home (`src/ui/Home.tsx`) drawn over it for a returning player and the new-idea card (`IdeaCard`, `IdeaGlow`, levels and timeline in `src/ui/levelIdeas.ts`) on levels that bring in an idea; `chapter/[chapterId].tsx` is one chapter's levels as board pictures (the game's back arrow, Android back, the result card's Levels and the L key open the current chapter's), and `levels.tsx` is the chapter cards one step up, with Reset progress, whose back arrow goes up to home. Both open over the game, which stays mounted underneath; `src/ui/levelsNavigation.ts` links them. After a chapter's last level the result card opens the chapters.
- `src/state/`: the Redux Toolkit store (`store.ts`), which calls the engine, the player's settings slice (`settings.ts`, saved whole by `src/ui/useSettings.ts`), the player's progress slice (`progress.ts`: best moves per level and the last win; solved, ★ and unlocking are worked out from the bests in `levelProgress.ts`, never saved), resuming the board the player left (`resume.ts`: the game slice keeps one letter per undo-history step, and replaying them rebuilds the board and its undo history), all saved by `src/ui/useProgress.ts` (the bests and current level after a win or level change, the board when the app is put away, never on a move), whether home is open and the saved progress has loaded (`session.ts`; nothing draws until it has), the palette ids and the seeded shuffle bag that picks each level's palette (`palettes.ts`), and the dev logger (`logger.ts`). No React Native imports, so Vitest tests them.
- `src/ui/`: React Native components (`Board`, `BoardTile`, `Player` (the Pebble), `Crystal` (the Beacon star), `CollectBurst`, `BoardPicture` (a level's start as one small SVG, shapes from `boardPicture.ts`) for the levels screens, `TouchPad` for the swipe and tap area under the board, `SeekArea` round the board (a resting finger walks the Pebble toward it; a stroke is a swipe), both on `useHoldGesture` and `useHeldMove` (held keys, taps, swipes and seeks repeat at one beat, `HOLD_REPEAT_INTERVAL` in `motion.ts`), `ResultCard` that rises over it once a level is won (moves against par, best, Next), `IconButton` for the header buttons and Undo/Restart, `ColourPicker` and `MoreSheet` (vibration, tap moves, language, the web's keys) on a shared `PickerSheet`, and `AppColours` for the app colours in React context), their animation hooks, and their pure helpers: `boardLayout.ts` (floor colour, box outline, portal seams, tile size, the touch area's height per phone), `motion.ts` (slide, bump and flip timing from engine events), `pieceLooks.ts` (the Pebble's poses and eyes, the star's state and rings, all from engine events), `commands.ts` (keys, swipes and tap zones), `seek.ts` (the seek's next step: shortest walk over floor, a push or portal only onto the very next tile), `winResult.ts` (par badge and best for the result card), `haptics.ts` and `sounds.ts` (which cue a move plays, and when; the web plays sounds through Web Audio in `webSounds.web.ts`), `i18n.ts` (PT/EN text, including every level's name and each idea's tip), `theme.ts` (the only place with colour codes: the board palettes and the app colours derived from them).
- `assets/sounds/`: the sound effects, written by `node scripts/make-sounds.mjs`. They are synthesised, so the repo owns them; change a sound in the script, rerun it and commit the files.
- `src/tools/solver.ts`: breadth-first solver on top of the engine.
- `tests/levelFingerprints.json`: a fingerprint of every level's board. Saved bests are kept by level id, so a changed board fails `tests/levels.test.ts`: give it a new id, or, if old bests still hold, run `node scripts/level-fingerprints.mjs` and commit.
- `tests/`: engine, store, UI helper and comparison tests. Tests import only pure TypeScript, never React Native components. `tests/legacy/` is a verbatim copy of the original rules and levels, kept only so `compare.test.ts` can check the engine against them. Don't edit or restyle it.

## Rules the code must keep

Specs live outside the repo, in the project files: `specs/portal-spec.md` and `specs/goal-tile-spec.md`. The key points:

- Portals are stored on edges (`{ row, column, side: 'right' | 'down' }`), not on tiles. Their two sides always have different colours, so only one side can be pushed at a time. A pushed tile carries the portals on its four edges, including the one on its leading edge. The tile that slides back carries none. A flip moves no portals.
- A push is refused if, afterwards, any portal would have the same colour on both sides or would face off the board (portal rule 6). Nothing can be pushed onto a crystal, but a crystal tile can itself be pushed.
- A push swaps whole tiles: the tile layer moves (colour, crystal), and a future board layer (pads, holes, walls) must stay put.
- The board draws in layers: the floor is one rectangle, and every tile sits on it. Boxes (tiles in the player's colour) are inset with rounded corners (`BOX_INSET`, `BOX_CORNER_RADIUS`), so the floor between them is their outline; floor tiles are full squares in the floor colour. Don't go back to per-tile borders; they left seams on phones.
- A box's portal side reaches the whole cell edge and curves out into it, and the portal is a glowing half-pill seam on the floor side of that edge. A flip grows the old boxes into full tiles, swaps the floor and player colours halfway, then shrinks the new boxes out (`FLIP_GROW_DURATION`, `FLIP_SHRINK_DURATION`).
- Colours are game values (`'black' | 'white'`). Hex codes belong only in `src/ui/theme.ts`. Each level is drawn in one of the board palettes there: `black` is always the palette's dark colour and `white` its light one. Undo and Restart keep the palette; selecting a level draws the next one. A new palette must pass `tests/theme.test.ts` (tile contrast for colour-blind players, portal seam, app text).
- Winning sets `status: 'won'` once every crystal is collected, and further moves are blocked.
- New mechanics go into the engine as a new tile kind, tile property, portal kind or win condition, never as a branch in the renderer. Bump `LevelData.version` when the level format changes.

## Code style (the owner's preferences)

- **Name every variable for what it holds**, including loop variables, callback parameters and destructured values: `portal`, `tileIndex`, `direction`, `event`, `levelData`. No one- or two-letter names (`s`, `d`, `i`, `e`, `t`, `r`, `el`, `dx`) and no unclear abbreviations (`col` → `column`, `cols` → `columnCount`).
- Exceptions, agreed with the owner: well-known conventions stay short. That means `t()` for translations and the Redux shapes `(state, action)` in reducers and `store => next => action` in middleware. Generic type parameters still get descriptive names (`ElementType`, not `T`).
- **Arrays and other collections are plural** (`tiles`, `portals`, `movedPortals`, `pastStates`). A count is `somethingCount`, and a map is `valuesByKey`.
- Match the surrounding comment style: a short header comment per file and comments that explain why, not what.
- Keep the engine pure and covered by tests. A rule change gets a test in `tests/engine.test.ts`. If it deliberately changes old behaviour, also update the stop conditions in `tests/compare.test.ts` and say why there.
